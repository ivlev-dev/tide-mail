# Sharded index

Индекс разделён по аккаунтам на 16 шардов.

## Маршрутизация

```text
shard = fnv1a(account_id) % 16
```

- Все документы аккаунта попадают в один `SearchIndex`.
- `account_id`-запрос идёт только в свой шард.
- Глобальный запрос обходит все шарды параллельно через rayon и мержит top-k.

## Postings

Внутри каждого `SearchIndex` postings дополнительно разбиты на 16 шардов по хешу терма. Это уменьшает размер отдельных HashMap и локализует обновления.

## Apply

Apply-поток обновляет нужный account-shard; `delete`/`flags` ищут владельца по шардам, `move` между аккаунтами переносит `Doc` в целевой шард.

## Snapshot

Снапшот сериализует `ShardedIndex` целиком (Vec<SearchIndex>). Старые снапшоты с другой версией отбрасываются, выполняется полный replay.

## Блокировки

Каждый шард имеет собственный `RwLock<SearchIndex>`. Запись в один аккаунт не блокирует поиск/запись других аккаунтов. Общего внешнего lock больше нет.

## Кэш запросов

`ShardedIndex` кеширует до 512 результатов на шард. Версия индекса инкрементируется при insert/delete/flags/move, старые записи игнорируются. Повторный одинаковый запрос не пересчитывает BM25.

## Ограничения

- Postings внутри шарда имеют 16 сегментов, но защищены одним lock шарда.
- Количество шардов фиксировано (16).
- Количество шардов фиксировано (16); для очень больших инсталляций нужен конфиг.
- Глобальный поиск мержит `offset+limit` из каждого шарда; при больших offset возможна лишняя работа.
